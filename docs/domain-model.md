# Shoots domain model



The ubiquitous language. If a word is not here, it is not a thing.

The product language below was locked on 2026-08-25 and corrected from real-phone use and Shoot-level product work on 2026-08-26. Experiment, Finding, Technique Map, Change, Shot, and Run are current across code and UI. Scene, Shoot, deterministic Shoot Record synthesis, typed Scout outcomes, the first persisted Mine/Inspiration boundary, scoped Photographer Signals, corrected Explore, and evidence-bound Shoot and Experiment Deconstruction drafts now exist. Only the legacy `skills` Firestore collection key and the migration-target class name `TechniqueState` remain. Overall and element scores are not stored. The numbered history retains old identifiers only while describing a superseded implementation; decisions 52 through 140 and 142 are the current contract wherever history conflicts.



## The loop



Shoots is an event-driven control loop: watch, assemble, read, remember, plan, verify, write back, and keep an audit trail. The claim is the completed learning work and the artifacts it leaves, not the number of agents.



```

Android Phone Source receives a Shot                                 (watch)
  → Ingest reads file, EXIF, Tone, Motion, grid, and video frames
  → Analyst produces measured and visual Evidence, Findings, and a reading
      ├→ Cartographer updates Technique Map and Tendency Profile
      └→ Judge, only for an explicit Reproduce submission
           → Verdict or explicit abstention
           → Scribe writes the reviewed Shot back to Drive

capture continuity groups Shots into Scenes and one Shoot             (assemble)
  → every member Run settles or ends terminally
  → Shoot synthesis records what repeated and varied
  → Experiment Evidence separately tests what became repeatable
  → Cartographer recomputes Profile, Technique Map, Change, and Journey
  → Scout chooses supported help and records rejected routes
  → Scribe attempts one Deconstruction draft

manual reference import → Inspiration study → optional Experiment Direction
  → never enters the Photographer's Technique Map, Profile, Change, or Journey

every step → ActivityEvent; every accepted Shot → one durable Run      (audit)
every closed Shoot → one terminal Shoot Record                       (audit)
photographer → shutter, optional Experiment participation, Keeper, Intent, and source role (signal)
Live Scene Session → temporary audio + Scene frames → question, move, or guide

```



## Nouns



**Photographer.** The person whose Shots, Evidence, Experiments, Keepers, Intent, and Journey belong to one record. The web audit desk and Android Phone Source belong to the same identity and record.

**Shot.** One still or video file from a Drive import or Android direct ingress. Identified by a stable source reference; a redelivery of that reference is a no-op. Carries EXIF or VideoMeta, Tone measured from pixels, Motion measured across a clip, the grid spec the Analyst saw, and blob paths for the original, gridded image, contact sheet, and thumbnail. A Shot joins an Experiment only through an explicit `experiment_id` or later explicit selection.



**Technique.** One entry in `domain/taxonomy.py`. Has a family (composition, light, exposure, lens, color, video), a cue the Analyst looks for, and optional hard EXIF bounds. The catalogue is finite so Evidence and Criteria stay checkable. Legacy source-order metadata named `level` and `requires` is not sent to the photographer and does not gate Analyst, Scout, Technique Map, or UI.



**Evidence.** The Analyst's claim that a Shot demonstrates a Technique, with confidence 0–1 and the cells where it is visible. Hard Evidence is EXIF; soft Evidence is vision. Soft Evidence below `judge_min_confidence` (0.6) does not count.



**Finding.** One checkable issue or observation about a Shot. A measured Finding carries the figure and rule that produced it (`domain/findings.py`, and `imaging/findingmark.py` draws it on the pixels it was computed from). A model Finding stays labelled as opinion; nothing produces one yet. A Finding may be excused by corroborated Technique Evidence or explicit Intent, which is why detection runs after the vote. New detection has three scoped Findings: elevated camera-shake risk from EXIF, highlights clipped beyond the pixel threshold, and a strong measured colour cast not explained by corroborated Technique Evidence. `no_centre_of_interest`, `split_horizon`, and `off_guide_subject` remain readable legacy ids but are not emitted: subject extent, horizon position, and distance from a guide are neutral composition Evidence, not proof of error or accident.

**Analysis.** Everything recorded about one Shot: Evidence, Findings, composition read, measured facts, model observations, critique, and the model and prompt version that produced the visual reading. It stores no overall or element score. A model reading is traceable to its inputs, not mechanically reproducible from a calculation version.



**Move.** One concrete next-capture or crop suggestion with its reason, warrant, and any Technique ids it deliberately challenges. A subject Move carries `from_cells` and `to_cells` and may be drawn as an arrow. A crop carries only the region that survives. A camera Move carries no cells because a viewpoint change is not a vector inside the old frame. The warrant is `visible_conflict`, `subject_separation`, `frame_edge`, `light`, `guide`, `variation`, or legacy `unspecified`. Challenge ids come from the Technique catalogue and let the teaching receipt refuse advice that undoes the Technique it just praised; guide conformity and deliberate alternatives belong outside corrective Shot teaching.

**Visual Mark.** One drawable pointer attached to one step of a Shot's visual story. It may be a region, line, enclosing frame, point, measured Finding, subject Move, crop, or whole-frame boundary. Its cells and target cells come from the same stored Evidence, observation, Finding, or Move as the sentence. A Visual Mark never invents an object contour or a direction that the source did not provide.

**Visual Path.** One ordered sequence of cell references describing a visible edge, trail, boundary, axis, or flow from its near origin toward the subject or named target. Multiple paths remain separate. A Visual Path is model-located Evidence until a rendered-overlay check confirms it; unordered Evidence cells are a region and never become a precise line.

**Visual Region.** One bounded group of cells with one finite role, such as subject, reflection, foreground, repeated instance, exception, light, shadow, warm, cool, sharp, or blurred. Regions stay separate and ordered through consensus. A pair is two regions, depth is ordered planes, and repetition is several instances; none may flatten into one bounding rectangle. Like a Visual Path, a Visual Region is a located model read until code refines or measures it.

**Visual Evidence Artifact.** One code-rendered explanation attached to Technique Evidence. It may contain a measured pixel map, refined geometry bounded by the Analyst's source cells, an EXIF receipt, or an explicit unresolved result. It records its authority, renderer version, source Shot digest, metric and legend where measured, verification state, and fallback reason. The model never emits its pixels. A measured map proves only its stated measurement: for example, a sharpness map does not by itself prove shallow depth of field.



**Tone.** What the pixels say about colour and light, measured at ingest in `imaging/tone.py`: colour temperature, cast, saturation, the dominant hues and the angle between them, the warm and cool shares, luminance percentiles and clipping. Exif for everything the camera did not write down — every real file reports auto white balance, so the camera records that it chose and never what it chose. `domain/tone.py` is the arithmetic on top, the way `domain/exposure.py` sits on Exif.

**Motion.** How the camera itself travelled, measured between consecutive frames in `imaging/motion.py` and read in `domain/motion.py`. Signed drift in frame widths, the mean and largest step, direction reversals and the share of steps that did not move.

**Technique Map.** One longitudinal record per photographer and Technique (`TechniqueState`, `domain/technique_map.py`). Three states: `unobserved`, `observed` once the Evidence has seen it, `recurring` after three corroborated sightings. Recurrence, explicit Reproduce attempts, Reproduce Criteria outcomes, distinct Scene coverage, conditions, and positive Keeper counts remain separate evidence; none collapses into a skill score. Corroborated Evidence moves the state and model scores move nothing. Time moves nothing either — what recurred keeps having recurred, so there is no decay and no `rusty`; age alone is never an Experiment Direction.



**Experiment.** One optional, bounded question to try, selected by Scout from the photographer's record or explicitly requested. One Experiment may remain open as the offered focus, but the camera stays free by default and unrelated Shots do not become attempts. Its type is `explore`, `reproduce`, or `compare`; each type has different completion evidence. Status is `open`, `completed`, `left`, or `expired`. `skipped` remains a legacy stored value until migration.

**Variation.** One optional route inside an Explore or Compare Experiment. A Variation suggests a different decision, not a correct answer. Explore offers two to four Variations that may include inversion or deliberate rejection of the obvious approach. Compare names the alternatives that hold one variable in focus. Choosing no Variation is valid.



**Criteria.** A check declared before a Reproduce result. `exif` holds bounds the Judge checks mechanically, `vision` names Technique ids the Analyst must see above threshold, and `text` is the plain-language version. Explore uses Variations and observations, not Criteria. Compare uses paired Variations and an optional photographer preference.



**Verdict.** The Judge's supported result for one Shot explicitly submitted to a Reproduce Experiment. It records each Criteria check, relevant confidence, and feedback. If required Evidence is unresolved, Judge records an abstention ActivityEvent and creates no Verdict. Explore and Compare create no Verdict. A Verdict says whether Reproduce Criteria were met, never whether the Shot is good or the photographer improved.



**ActivityEvent.** One durable record per agent step. The live feed (SSE) is a view of these; Firestore is the truth.

**Run.** The durable stage account for one accepted Shot. It records Ingest, Analyst, Cartographer, Scout, Judge, and Scribe outcomes separately, including retry, abstention, non-applicability, and external-write results. A Run becomes complete only when every required stage has settled; a terminally unreadable Shot ends the Run with a terminal result. ActivityEvents explain what happened, while Run state decides whether the work is finished.

**Scene.** One photographic situation at one place and time containing one or more Shots inside a Shoot. Scene membership must come from capture continuity or explicit grouping, not visual similarity alone.

**Shoot.** One natural period of Camera activity containing one or more Scenes. Capture continuity assigns membership, with an explicit correction allowed; visual similarity alone does not. A Shoot is `open` while capture-continuous Camera media may extend it, `closing` after the inactivity gap while known member Runs settle, and `settled` when its current revision has one terminal Shoot Record. A late Camera Shot or Photographer correction increments the revision and returns it to `closing` without mutating the earlier record. A Shoot is not an Experiment and does not imply that any member joined one. A Shot may belong to both one Shoot and one Capture Session because those records answer different questions.

**Shoot Record.** The durable result of one settled Shoot: exact Scene and Shot membership, member coverage, observed decision distributions, Variations, Technique Evidence, positive Keeper signals, provenance, and the recorded Scout outcome. It is a learning record, not a quality report or score.

**Tendency.** A neutral repeated pattern across Shots. It describes a distribution or low-variance dimension and carries its Shot set, count, blind spots, and calculation version. It does not imply a problem or Intent.

**Keeper.** A Shot the photographer positively marks as valued. Unmarked means unknown, not rejected. A Keeper is the only direct taste signal in v1 and never changes Criteria or Technique Map state.

**Baseline.** The measurement an Experiment was aimed at, frozen at issue time, before any result exists. It carries the dimension it came from, the citation the photographer was shown, the bucket counts, the `CALC_VERSION` that produced them, and the Shot set they were computed over. A Baseline exists only where the photographer's own tendency chose the Technique; advice picked for another reason is never graded against a tendency it was never aimed at.

**Change.** A measured difference between comparable earlier and later behaviour. Change may be `changed`, `unchanged`, or `insufficient evidence`. It is not automatically improvement and does not prove an Experiment caused it.

**Comparability.** Why a Baseline and the present could, or could not, be set beside each other: `comparable`, `too few shots`, `different arithmetic`, `different model reading`, `baseline shots missing`, `unknown dimension`, or `unrecorded sample`. Only `too few shots` can resolve itself, so only it is checked again; the rest are written once and settled.

**Experiment Record.** The durable record of one Experiment's question, reason, type, frozen Baseline, explicit Shot set, and Change. Explore also records Variations tried and observed Evidence. Reproduce freezes one exact Keeper Shot as its reference, then records every explicitly associated result Shot, its Criteria, abstentions, and Verdicts. Compare records paired Variations and any photographer preference. It is the checkable artifact left by the Scout, Analyst, Judge where relevant, and the photographer's signals.

**Experiment type.** Which of three questions an Experiment asks. `explore` asks what happens across several optional Variations and never produces a pass or fail. `reproduce` tests whether a Keeper-associated pattern can be made deliberately and may use Criteria plus a Verdict. `compare` changes one variable, preserves both alternatives, and asks which result the photographer values. Reproduce and corrected Explore are implemented. Compare remains later work; Scout stays silent rather than issuing a substitute.

**Experiment Direction.** A neutral mapping from evidenced Photographer work to one Technique that could be tested or explored. It may come from a Tendency, Inspiration study, or a corroborated Technique visible in a Shot when Keeper Evidence supports Reproduce. The Photographer may save that question for later or leave it. A saved Direction is not an Experiment: it has no Criteria, deadline, Capture Session, Verdict, or claim about Intent. It stores its source Shot, Technique, and exact Keeper warrant. Only an explicit "Try it today" starts Scout, creates an Experiment when the warrant still holds, and permits Android to reserve a Capture Session. Without a supported Direction or an explicit Photographer request, Scout stays silent.

**Scout Recommendation.** One ranked, evidence-backed Experiment Direction prepared from a settled Shoot and the Photographer record. It shows one primary idea and may preserve other supported ideas as alternatives. A Recommendation is not an Experiment, Intent, Criteria, Capture Session, or claim about what the Photographer meant. "Try this" accepts one exact option and only then creates the Experiment. "Another idea" changes which stored option is shown and creates nothing. "Not today" leaves the Recommendation without guessing why. Optional Photographer feedback may record explicit Intent or preference, but the Recommendation never requires an answer before showing useful work.

**Journey Update.** The evidence-backed longitudinal conclusion written when the photographer's record meaningfully changes. Each clause cites measured Evidence, corroboration, or an explicit photographer signal.

**Intent.** The optional statement of what the photographer is trying to make in a Shot, Scene, or Experiment. Inferred purpose is model opinion. Explicit Intent outranks an offered Experiment when their directions conflict. No persisted Intent input is built yet; until it exists, the system may not speak as though it knows one.

**Phone Source.** The narrow Android client that makes the phone's normal Camera album an event source. After one explicit permission grant, it observes only approved Camera media, identifies unseen files by a stable local reference, and schedules their upload to Shoots. Full media access permits automatic future imports. Selected-media access permits only explicit import and must never be presented as automatic. It does not replace the system camera, read screenshots or messaging folders, or edit and delete local media.

**Capture Session.** One explicit, bounded Android handoff from an open Experiment to the system camera. It reserves the Experiment before the camera opens, then freezes the exact ordered Camera source references the photographer included when they return. The explicit session assigns those Shots; capture time never does. A Capture Session is not a Shoot or Scene, does not imply that its Shots share one place or subject, and never gives Shoots control of the shutter. Reproduce uses its members for Criteria outcomes; corrected Explore uses them for Variation observations without a Verdict. It may be `reserved`, `committed`, `processing`, `settled`, `cancelled`, or `expired`.

**Companion.** Shoots' continuing relationship with the photographer across Shoots. In the Taskmaster build it appears through one optional Experiment, proof-carrying results, and honest limits when Evidence is insufficient. The earlier CameraX viewfinder, Scene Probe, and Live Scene Session are parked historical directions, not the Android product boundary, hackathon proof, or current roadmap.

**Live Scene Session.** A temporary, explicitly summoned conversation while the photographic decision is still open. Android sends microphone audio and low-rate Scene frames through the Shoots service to Gemini Live. The Companion may ask one useful question, offer one Variation, or call a guide tool using cell refs. The photographer may interrupt it. No frame becomes a Shot until the shutter, and the model has no shutter tool. Raw Scene frames and audio are not stored; transcript, explicit memory, and tool actions follow the same provenance rules as other ActivityEvents.

**Scene Probe.** A temporary capture for inspecting the current Scene without creating a Shot. It is the silent fallback when a Live Scene Session is unavailable or the photographer does not want audio. The server may use explicit Intent and an optionally selected Experiment, then returns one question, Variation, move, or refusal. The bytes are discarded after the response. A Scene Probe never enters the Shot archive, Technique Map, Tendency Profile, or Journey; only its ActivityEvent is durable.

**Inspiration.** Sourced reference material the photographer explicitly chooses to study. It may carry its own bounded Analysis and Deconstruction and may support an Experiment Direction, but it is not a Shot, Keeper, or Photographer Evidence and never enters the Technique Map, Tendency Profile, Change, or Journey.

**Deconstruction.** A shareable, image-led explanation of one Shot, Scene, Shoot, Experiment result, or Inspiration, rendered from stored Evidence and labelled model reads. A carousel is one presentation of a Deconstruction. It is a draft the photographer may export, never an automatic social post, quality grade, or source of longitudinal truth.

**Provenance.** The record of how a claim was produced. Deterministic claims carry their calculation version and exact Shot set. Model-read claims additionally carry the Analysis model, prompt version, and a per-Shot digest of the exact soft fields used. Provenance promises replay for arithmetic and traceability plus revision detection for model interpretation; it never calls model output deterministic.



## Agents



| Agent | Trigger | Reads | Writes | Model |

|---|---|---|---|---|

| Ingest | `media.new` | Drive import or direct Android upload | Shot, blobs, Tone, Motion | none (ffmpeg, Pillow, numpy) |

| Analyst | `media.ingested`; target `shoot.ready` | one Shot; target settled Shoot facts and member Analyses | Analysis; target Shoot-level decision and Variation synthesis | gemini-3.7-flash × 4 per Shot; one bounded Shoot reader only where arithmetic cannot settle the comparison |

| Cartographer | `media.analyzed`; target `shoot.synthesized` | Analysis, Shoot Record, and Technique Map | Technique Map; Profile, Change, and Journey recomputation | none (pure) |

| Judge | explicit Reproduce result analysed | Analysis, Experiment | Verdict and Reproduce state | gemini-3.7-flash for feedback only; checks are pure |

| Scout | first settled Shoot, scheduled tick, completed Experiment, explicit request | Shoot Record, Technique Map, Tendency Profile, Experiment history, Keeper and Intent signals, constraints | typed choice to explain, ask, offer Explore, offer Reproduce, or stay silent; one Experiment when permitted | gemini-3.7-flash + Search grounding where a reference is useful |

| Director | manual legacy call only | open Experiment and Technique | optional generated reference clip | gemini-3.7-flash, veo-3.1-fast; outside the core product |

| Scribe | `media.judged`; `shoot.settled`; explicit Deconstruction request | annotated Shot, Shoot Record, Analysis, Experiment result, selected Keeper | reviewed copy and optional Deconstruction draft | Pillow; bounded Gemini writer for an explicitly requested Deconstruction |

| Coach | Live Scene Session or reviewed-Shot summon | current Scene frames, audio, optional Experiment, Intent, Analysis where available, explicit memory | question, Variation, move, guide tool, optional Experiment or remembered fact, ActivityEvent | gemini-live-2.5-flash-native-audio; gemini-3.7-flash Listener |
| Android Phone Source | approved Camera media changes or explicit picker selection | unseen Camera items, selected open Experiment, revocable device session | stable source reference, original Shot bytes, import/retry state | none; WorkManager and MediaStore |

| Scheduler | Cloud Scheduler | photographers and open Experiments | renews Drive channels, expires Experiments, triggers Scout | none |



Cartographer and Judge state changes are pure code. The Technique Map, Criteria checks, and Change records must be reproducible from stored data. A model cannot settle its own Reproduce Experiment, choose a Compare preference, or call its suggestion an improvement.



## Decisions



1. **Drive is the only input.** No upload endpoint in v1. The PWA's "Shoot" button uploads to the Drive folder through the Drive API, so phone and desktop use the same path and the watch channel is the only trigger.

2. **Finite taxonomy.** The model tags from a list. Unknown ids are dropped and logged.

3. **Cells, not pixels.** Reused from Visual QA: the grid adapts to aspect ratio (~64 cells), refs are chess-style, `domain/grid.py` does all conversion.

4. **Hard evidence first.** The Judge checks EXIF bounds before looking at vision tags. An experiment whose technique has EXIF bounds cannot pass on vision alone when EXIF is present and fails the bounds.

5. **Photo first, video supported.** Videos become a contact sheet (scene-cut frames, up to 12, tiled 4 wide) plus ffprobe metadata. Video techniques are judged on the sheet. No per-frame analysis in v1.

6. **One experiment a day, one open at a time.** Anything added to the folder while an experiment is open is an attempt at it (or a shot tagged with the experiment id by the Shoot button). A failed attempt appends a verdict with feedback and the experiment stays open until its TTL; the first passing verdict closes it and the Scout issues the next. Skipping is the human gate and is logged, never deleted.

7. **Pipeline stages are transport-agnostic.** The same stage functions run chained in-process locally and behind Pub/Sub push subscriptions on Cloud Run. Every subscription has a dead-letter topic; every stage is idempotent on shot id.

8. **Secrets stay out of Firestore.** The Drive refresh token lives in Secret Manager (prod) or `.blobs/tokens` (local). Firestore holds the user's Drive folder id and page token only.

9. **Gemini 3.7 via the Vertex global endpoint; Veo and Gemini Live via us-central1.** Verified per model on 2026-08-23; each has its own `*_location` setting. App infrastructure in asia-southeast2.

10. **Voice review is a relay, not a browser-side Live client.** The phone opens one WebSocket to this service per shot; the service opens the Gemini Live session with the gridded frame and the Analyst's read as the first turn, and relays 16 kHz PCM in and 24 kHz PCM out, plus transcripts. The browser never holds a Google credential and the briefing never leaves the server. The session ends as one ActivityEvent with the transcript, so the feed shows what was discussed.

11. **A service account reads the folder; OAuth stays non-sensitive.** The shared consent screen is in production and unverified, and `drive.readonly` is a restricted scope, so the app never asks for it. On Connect, the app creates the user's `Shoots` folder with `drive.file` (non-sensitive) and shares it with `shoots-ingest@…iam.gserviceaccount.com` through the Drive API. The service account watches, lists and downloads whatever lands in that folder, whoever uploaded it. Sync is a folder listing keyed by Drive file id; a `files.watch` channel on the folder (Drive reports child changes on it) calls `/drive/notify`, the Scheduler renews channels before their one-day cap, and `/tasks/sync` polls as the fallback. Local dev has no public URL, so it has no channel and polls; the sync code is the same.

12. **Experiment delivery is Web Push to the PWA, not email.** Gmail send is a restricted scope with the same verification problem. Push lands on the phone, which is where the experiment is acted on anyway.

13. **Historical: the reference-clip trial never belonged in the work.** This automatic Director/Veo path was removed by decision 59. The retained manual legacy call is outside delivery, Criteria, Verdict, Change, and Journey, and discards its blob if the Experiment closes while rendering.

14. **One stage, one push subscription.** Handlers register under a stage name; `/pubsub/<stage>` delivers to exactly that handler. Cartographer and Judge both read `media.analyzed` but retry and dead-letter independently, and a replay from a DLQ re-runs one stage, not the fan-out.

15. **The review goes back where the Shot came from.** After the Judge, the Scribe writes `Shoots/Reviewed/<name> — <Technique or Finding>.jpg` into the user's Drive as the user (`drive.file`): the Shot with the composition read drawn on it and the critique, changes, and any Verdict in a caption band and the file description. No score enters the name or review. It shows up in the Drive and Files apps on the phone and can be shared as-is; the app is optional for reading it. The Judge therefore always publishes `media.judged`, Verdict or not, so the first write already carries the outcome.

16. **The Scout decides when, not just what.** Each technique has a light window (`taxonomy.LIGHT`); the user's location is the GPS of their own newest frame, never asked for. The experiment is stored at issue time with `deliver_at` and a reason ("fifty minutes before sunset where you last shot"); the push goes out on the five-minute tick when that moment comes. Solar times are NOAA's equations in `domain/sun.py`, UTC throughout; the phone formats them.

17. **Talking to the Coach is how the user steers the planner.** There is no settings form. After a voice session the Listener extracts standing facts ("no tripod", "shoots at lunch near the office") into `User.constraints`; the Scout's ranking drops techniques whose `taxonomy.NEEDS` gear is missing and its brief is written inside the notes. The Coach is briefed with the same facts so it never asks twice.

18. **A Shot is read by a panel and bounded by code.** The Analyst is an ADK `SequentialAgent`: a `ParallelAgent` runs three lenses that differ in instruction *and* input (Technician: EXIF + gridded image; Composer: gridded image only; Storyteller: clean image only), then a Synthesizer writes the critique from their readings. What the Shot shows is a vote in `domain/panel.py`: two lenses, or the owning lens at ≥ 0.75; confidence is the mean over those who agreed, and the agreement count travels with the Evidence to the Judge, feed, and phone. Per-reader rubric notes may guide synthesis inside the call, but no element or overall score is stored or shown. A panel below quorum is not a reading; the stage retries. Sources and reasoning are in `docs/technique-evidence.md`, as are the citations behind every EXIF bound.

19. **The Composer's crop must beat the original on the pixels.** `suggested_crop_cells` is an opinion until `agents/crop.py` renders the crop, has a rater score original and crop as finished frames, and keeps it only if composition rose; the rater may propose one alternative, so at most two rounds. A crop that failed is cleared, so neither the overlay nor the Drive review ever draws an untested suggestion. The loop is Python, not an ADK `LoopAgent`, and that is a choice rather than a constraint: this note used to say an `LlmAgent` with an `output_schema` cannot take tools, which ADK 2.7.1 contradicts outright — tools are exposed during the thought loop and structure is enforced only on the final output. What stands is that injecting a freshly rendered image mid-invocation needs a `before_model_callback` and that path is untested, `LoopAgent` is itself deprecated in 2.7.1, and a bounded two-round Python loop is testable with a number.

20. **Arithmetic before opinion.** `domain/exposure.py` derives EV, the handheld limit, freeze thresholds and the 500-rule ceiling from EXIF and hands them to the Technician and the Judge as facts ("1/40 s is slower than the 1/46 s handheld limit"). The lens is told these are arithmetic, not impressions.

21. **The bar is one of your own earlier frames.** The Judge's feedback gets an earlier shot of the same Technique (from `TechniqueState.shot_ids`) as a second image with its observations, and must say in one sentence what is different now. `Verdict.compared_with` records which Shot. It used to be the *highest-scoring* earlier shot, which let a number nobody may see decide what "your best" means — the model's taste choosing the bar the photographer is measured against. The order is now a Keeper first, because that is the only opinion here that is actually theirs (decision 45); failing that the frame the panel corroborated hardest, which is a claim about the Evidence rather than about the frame's worth; failing that the most recent, which at least says "since then". Nothing in the chain reads a score, and the surfaces say "your earlier one", never "your best".

22. **Pre-flight before upload.** For an experiment, the Shoot button sends a 640 px preview to a one-call check of the experiment's SEEN criteria (`agents/preflight.py`, ~8 s) and shows "shoot again" with a concrete fix before the frame is sent. Camera settings are never guessed from a preview; that stays with the Judge.

23. **Evidence on demand for video.** The Composer may name two timestamps; `agents/scrub.py` pulls those exact frames with ffmpeg, grids them, and votes as a fourth lens on camera-move techniques only. It rates no elements.

24. **The Coach acts.** The Live session carries three function declarations: `issue_experiment(technique_id, reason)`, `remember(missing_gear, notes)`, and `technique_map()`. Function calls are answered by `services/coach.py` inside the relay and echoed to the phone as “→” lines; an Experiment issued by voice is an ordinary timed Experiment with fixed Criteria. It does not invoke Director. The Listener remains as the post-session fallback. Cost: the Scout's research runs inside the tool call, so the photographer waits about 40 seconds for the answer; a spoken “working on it” filler is the obvious next step.

25. **One screen, one state, one decision.** The web app's home is `Now`, and it renders exactly one of connect / seed / reading / Experiment / idle — never a dashboard of all of them. The Technique Map and audit trail live in `Journey`, the archive in `Shots`; a phone gets three tabs and no floating web shutter. The native Android camera is the capture Companion. Layout follows from that: media full-bleed, one hero line, Criteria in plain sentences, the action pinned in the thumb zone, and everything that explains rather than instructs behind a disclosure row. Three type weights (hero, body, meta) and one accent — amber, meaning “the agent decided this” — replace the seven-colour chip vocabulary.

26. **The first Experiment is not asked for.** A new account connects Drive and hands over enough existing Shots for a supported Direction. When the Cartographer updates the Technique Map, `scout.issue_first` fires only if the photographer has never had an Experiment; insufficient Evidence produces silence. After that only the daily tick and `experiment.closed` ask Scout to issue, and one atomic open slot prevents parallel Experiments.

27. **The Coach is text-first.** The session opens without the microphone: a WebSocket, the frame, and a text box that works from the first second, because a photographer in a gallery, on a street, or on a laptop without a mic still deserves an answer. The mic is one tap away. A question the user clicked ("why did this not pass") is sent as the opening turn, but only after the model's briefing turn completes — a second turn on top of a generating one is what produced the 1006 abnormal closures. One dropped session is picked up again silently, with the last question replayed.

28. **Two grids, two readers.** The cell mesh (`A1`..`G9`) is an addressing system: it exists so a lens can point at the bamboo pole and so code can map that back to pixels. It is not a compositional idea, and it never reaches the photographer at all: not as a mesh on the frame, and not as a coordinate in a sentence. The Synthesizer, the Judge and the Coach are told to place things in words ("the pole across the top"), and anything already written with cells is rewritten on the way to the screen and into the Drive review (`cells.plain`, `Grid.place`). Showing the machinery was itself the mistake: the reader has no grid to check it against. What the photographer sees is a *guide*: thirds, the phi grid, the diagonal method or a centre axis, chosen from the technique the panel agreed the frame is built on (`domain/guides.py`), with the subject's own centre drawn on it so the frame can be seen sitting on the guide or missing it. The readout ("sitting on the thirds point", "19% of the frame off") is withheld unless the read is finer than half a cell, which is why the Composer now also returns `subject_x`/`subject_y` in frame units — kept only when the point falls inside the cells the same lens named.

29. **A crop is not a vector, and a viewpoint is not a direction.** Every change carries a `kind`. `move` is a repositioning inside the frame and is the only thing drawn as an arrow; `crop` names the region that survives and is drawn by dimming what leaves; `camera` ("kneel to her eye level") is written as words and gets no mark at all, because a change of viewpoint has no honest representation on a flat image. A crop asked for as a move is routed into `suggested_crop_cells`, where the crop loop has to prove it on the pixels before anyone sees it. One instruction is drawn at a time, over a quiet guide and thin findings; the overlay used to draw four marks at equal weight and an arrow from a strip of sky to the middle of the frame.

30. **Colour, light and motion are measured, or they are not evidence.** Composition arrived with a grid, a guide, a subject point, a tested crop and four faults; colour and light arrived as adjectives, and they fire nearly as often — measured over the corpus, 0.94 and 1.06 sightings a shot against exposure's 0.94. A lens saying "the palette is cool" is an opinion the reader cannot check. So `imaging/tone.py` measures colour temperature, cast, saturation, hue relationship, key, tonal range and clipping off the pixels at ingest, and `imaging/motion.py` phase-correlates a dense low-resolution strip to measure how far the framing actually travelled. Camera EXIF cannot stand in for either: every real file reports auto white balance, and the contact sheet's tiles are seconds apart, which is why twelve video techniques were firing at 0.11 a shot. Two new faults follow the same rule as the other four — `blown_highlights` and `colour_cast`, each carrying its figure and each excused by the technique the panel agreed on, so a vivid sunset is not accused of a tungsten cast. Colour temperature is withheld when the frame sits too far off the Planckian locus for the number to mean anything: a frame of pure red is a red object, not 2655 K light.

31. **Each lens is told only what it owns; the Synthesizer is told everything.** The measurements are routed by `panel.OWNER_BY_FAMILY` — the Technician gets the exposure arithmetic and where the scale ran out, the Composer the temperature, the key and where the sun was, the Storyteller the palette and the hue relationship — and the three sets are disjoint, asserted by a test. Handing all three lenses the same numbers would buy anchored claims at the cost of the only thing a panel is for, three readings whose errors are not shared. The Synthesizer is the exception, because it writes the one paragraph the photographer is guaranteed to read: it gets every measured fact and must quote the one that carries the point it is already making. A critique that cannot cite the arithmetic is a critique any model could have written from the picture alone, which is what the Synthesizer's old contract — "you do not restate them, you write the words" — guaranteed it would be. Golden hour and blue hour are the two light techniques the sun can settle, so `domain/tone.py` places the frame against NOAA's sunrise and sunset from the EXIF time and GPS and the Composer is told; a claim of golden light three hours from the horizon is now disprovable.

32. **What translation cannot see is never claimed.** `domain/motion.py` settles `static_tripod`, `pan`, `tilt` and `whip_pan`, and says so; `orbit`, `push_in`, `tracking` and `rack_focus` turn on rotation, scale or focus, which phase correlation does not measure, so nothing corroborates or contradicts them and the lenses keep the last word. The measurement is checked against clips whose movement we chose — a window slid across a still at a known rate — and it lands within the (n-1)/n frame-interval factor of the truth. Naming the limit in the prompt is the point: a lens told that the measurement is blind to zoom will not read a push-in as a failed pan.

33. **The map tracks recurrence, because recurrence is what it can measure.** A whole-Shot score once credited every Technique in the Shot with the same number, which could not establish that any one Technique was done well. `domain/technique_map.py` instead counts sightings and corroborated sightings. `observed` is one sighting; `recurring` is three attempts with three corroborated. Judge chooses an earlier comparison by Keeper, then per-Technique corroboration, then recency. Decision 61 removed `score`, `elements`, `best_score`, and `last_score` from the stored domain; old keys are ignored and the migration removes them. The map claims only what Evidence supports and never grades ability.

34. **Arithmetic outranks the panel, and not only in the prompt.** `domain/motion.py` has always computed what the measured drift *rules out* — a clip that travelled 2.42 frame widths is not a locked-off tripod shot — and `motion.describe()` has always handed that sentence to the Technician and the Composer. Then it stopped: the only occurrence of the word `motion` anywhere in `domain/panel.py` was the string `"slow_motion"` in an owner override. The vote could not read the measurement, so a lens was free to claim `static_tripod` on that clip and the evidence stood, promoted a TechniqueState and reached the photographer. "Arithmetic, not opinion" was true of the prompts and false of the panel. `panel.aggregate` now takes `settled_for` and `settled_against`, two sets of technique ids that measurement has already decided. Against is a veto: the evidence drops however many lenses saw it and however sure they were, and the sighting travels on as dissent so the feed still shows what was claimed and what beat it. For is a corroborating vote, so a single lens noticing is enough, and the evidence records `measured` alongside the lenses that saw it at a confidence of 1.0 — a proof does not become less certain because a model was half sure, and arithmetic is the one voter in the system that cannot share the panel's blind spots, which is exactly what decision 33's corroboration bar is asking for. A technique the measurement settles *for* that no lens mentioned at all still creates nothing: evidence is a claim a lens made, and a measurement with no reading behind it is a gap in the panel rather than a sighting. The sets arrive as plain ids because the vote does not need to know which measurement settled them; motion supplies them today, and tone and exposure could supply more. Replayed on the corpus clip, `pan` moves from one lens at 0.85 — which decision 33 can never count as corroborated — to two votes at 1.0. Sources and the benchmark evidence behind the change are in `docs/video-findings.md`.

35. **The viewfinder runs arithmetic natively and asks explicitly.** The Android camera (`android/`, Kotlin + CameraX + Compose) runs clipping and pitch locally, paints zebras and thirds, shows the active Experiment, captures a Shot, and uploads it into the same ingest path as Drive. Ask captures a temporary Scene Probe, checks only the active Experiment's visible Criteria through the existing preflight agent, and returns one bounded move; it is not a chat thread and stores no image. After Analysis, the camera returns a praise-first pulse only when at least two readers agree above the Companion confidence threshold; the line carries its warrant and any Finding carries its reason. Open-ended Scene conversation is not built. What is painted is measured; what is said is a traceable model read.

36. **The Tendency Profile treats the photographer as a distribution.** Each readable Shot contributes to measurable dimensions such as height, distance, placement, light, dwell, subject type, and moment versus static. A Tendency is a narrow dimension, not a defect. `domain/tendency.py` computes counts from the complete readable archive; model-read dimensions are labelled and versioned separately. Keeper evidence is positive-only: the Profile may say where marked Keepers gather, never treat unmarked Shots as disliked or use them as a preference denominator. Counts and blind spots appear before claims. Scout may select only a Technique named by a cited Experiment Direction derived from this Profile, or one explicitly requested by the photographer.

37. **The Companion checks its own advice without grading the photographer.** An Experiment aimed at a Tendency freezes the exact Baseline, calculation version, Shot set, and relevant model-read provenance before any result exists. Later comparable Shots produce `changed`, `unchanged`, or `insufficient evidence` by domain arithmetic. The record does not claim that the Experiment caused the Change or that the Shots improved. Automatic retirement or replanning from repeated outcomes is not built; the durable Change is the honest work completed today.

38. **The panel and Judge may abstain.** When readers fully disagree, `panel.aggregate` records that no visual consensus exists instead of averaging opinions into a result nobody held. When required Criteria remain unresolved, Judge records why and creates no Verdict, leaving the Experiment open. The readings, disagreement, and abstention remain in the audit trail. Expertise includes knowing when the available Evidence cannot settle the question.

39. **Four words stay apart: Tendency, Change, Journey Update, Verdict.** A Tendency is a neutral repeated pattern. A Change is a measured difference between comparable Shot sets, not automatically improvement. A Journey Update is the evidence-backed longitudinal artifact that states what repeats, what recurs, and what changed, with provenance. A Verdict answers one Experiment's Criteria. Nothing inherits the authority of another word, and no model score is allowed to speak as the photographer.

40. **The Keeper is one optional tap and the only built source of taste.** The photographer may mark any Shot they value from Android or web. With enough marks, the Tendency Profile reports counts and shares among marked Keepers, such as “3 of 5 marked Keepers use side placement.” Without them, the Profile says less. Unmarked Shots are unknown, never rejected; Keeper feeds no Technique state or Criteria and is never second-guessed.

41. **The audience is the self-directed post-beginner hobbyist.** They have enough Shots for patterns to exist, already understand basic advice, lack a recurring mentor, and cannot tell development from luck. They want Keepers, proof of Change, an emerging identity, and an enjoyable practice. The product must not become school. This supersedes any professional workflow framing.

42. **The product answers a longitudinal question.** The canonical question is: "What patterns keep appearing across my Shots, and can I deliberately reproduce the ones present in my Keepers?" "Why are my Shots boring?" may introduce the problem, but Shoots cannot prove boringness. It can prove recurring behaviour and Change across comparable Shots.

43. **Experiment replaces Quest.** One active Experiment at a time preserves focus, but no daily cadence is mandatory. An Experiment is `explore`, `reproduce`, or `compare`. Explore widens an underused dimension. Reproduce tests whether a Keeper-associated pattern can be made deliberately. Compare changes one variable and asks for an optional photographer preference. Criteria and Baseline are fixed before results arrive. Only Explore is issued today; the type is recorded on every Experiment so the other two arrive without a migration.

44. **The work leaves an Experiment Record and a Journey Update.** Advice text is insufficient. The Experiment Record preserves its Tendency or Keeper reason, frozen baseline, Criteria, results, Verdicts, and Change. The Journey Update states what repeats, what became repeatable, and what changed, with source Evidence for every clause.

45. **Keeper is positive-only.** `kept` means valued. `unknown` means the photographer supplied no taste signal. Unknown Shots cannot become negative examples or the denominator of a preference claim. A future explicit rejection signal would be a separate domain concept and does not exist. This supersedes decision 40 wherever its rate calculation treats every unmarked Shot as not valued.

46. **Technique Map and Change replace ability language.** The user-facing states are `unobserved`, `observed`, and `recurring`. `solid`, `rusty`, level-up language, and the 1 to 10 score leave product surfaces. `Change` replaces `Progress` unless an explicit photographer goal and preference signal define what progress means. A Verdict answers Criteria only.

47. **The camera is a quiet Companion, and the boundary is stricter than the current build.** Built behavior is named in decision 35. The target may later add weather and place context only when relevant, remembered context, open-ended summoned conversation, and rare high-value interjections. Explicit Intent may eventually mute a conflicting warning. None of those target behaviors may be pitched as built. The photographer controls the shutter; hidden location history and the internal cell grid never reach the user.

48. **Agent depth follows from the honesty problem.** A hobbyist cannot audit an AI critic, so the system preserves what each claim came from. Versioned domain code owns thresholds, Criteria, corroboration, vetoes, transactional state changes, and comparability. Prompts own visual interpretation and language. The system can refuse, abstain, plan, remember explicit constraints and Keepers, and check whether comparable behaviour changed after its advice. It does not yet adapt future Directions from those Change outcomes, and it never claims causation or artistic improvement.

49. **Change has three answers, because two of them lie.** `moved: bool` could say the behaviour widened or that it did not, and everything that was neither had to pick a side — so a photographer who simply had not been out since read as advice that failed. `domain/tendency.change` now returns a `Change` with a `ChangeState` and a `Comparability`, and the third state is the one that makes the other two worth anything. Three floors decide it: `MIN_SHOTS_FOR_CHANGE` (a single frame can put a bucket on the board, and calling that movement credits the advice for arithmetic), `MIN_SCENES_FOR_CHANGE` for dwell (frames per scene is a ratio and needs more than one scene to be one), and a Baseline frozen under a different `CALC_VERSION`, which never becomes comparable and is recorded as such rather than skipped — a record holding no Change reads as though nobody looked. The count in the sentence is *frames taken*, not frames the dimension could read: height needs recorded pitch that Phone Source cannot recover, and light needs GPS, so forty imports carrying neither leave the totals untouched, and telling someone who shot forty that they shot none was the failure that forced the split. Only `too few shots` is re-checked, because only it can resolve itself.

50. **No outcome sentence may join a suggestion to a result.** A Change reports what the counts did; whether the Experiment is why is not available from two frozen counts. Every sentence `change` and `dwell_change` can produce is checked against a word list in `tests/test_selfgrade.py`, and the Journey writer is given the two facts separately with an explicit instruction that it may state both and may not connect them with *because*, *so*, *after trying it*, or *thanks to*. The photographer is free to draw the line themselves; the system is not, because it cannot tell a followed suggestion from a week that would have gone that way anyway.

51. **Provenance travels with the Baseline, and a claim without a sample says so.** Every Baseline records the Shot ids, the sample size and the `CALC_VERSION` behind its citation, so the figure can be replayed. No model or prompt is recorded there, because the citation is an f-string over counts rather than anything a model wrote. Experiments issued before this existed keep their citation and report `unrecorded sample`: their counts are still on disk, but nothing says how many frames they were taken over, so "shots since" has no honest value and the Change declines to invent one. The Journey Update does the same at its own scale — it refuses to diff against an earlier update written under a different `CALC_VERSION`, and re-baselines instead, because moving one bucket edge re-buckets the whole corpus and would report a week of change to someone who never picked up a camera.

52. **Ingest distinguishes retryable failure from terminal media failure.** A transport, storage, dependency, or transient decode failure leaves the Shot `new`, writes a retry ActivityEvent, and raises so Pub/Sub may redeliver it. Only a file proven unreadable or unsupported becomes `failed`. A `failed` Shot is terminal; a retryable attempt is not allowed to poison the idempotency key.

53. **One open Experiment is a storage invariant.** Scout does not check and then write. Storage creates the photographer-scoped open slot and its Experiment Record in one transaction; closing, skipping, and expiring release the same slot conditionally. Concurrent Scout runs may produce candidates, but only one can become open, and Judge never observes a claimed slot without its Experiment.

54. **Abstention produces no Verdict.** If required visual Criteria are unsettled and no hard measurement settles the result, Judge records the abstention and leaves the Experiment open. Missing EXIF remains explicitly unknown rather than being coerced to false. A Verdict exists only when every required answer is supported strongly enough to call.

55. **Keeper summaries use positive marks only.** Decision 45 forbids rates against unmarked Shots, so Keeper evidence is expressed as counts and shares among marked Keepers: for example, "3 of 5 marked Keepers use side placement." There is no keeper lift, rejection proxy, or taste claim whose denominator contains unknown Shots. This supersedes the rate and multiplier language in decisions 36 and 40.

56. **The longitudinal archive is the whole readable archive.** Tendency Profile and Journey calculations read every stored Shot that has a completed Analysis; queued, retrying, and unreadable files do not become photographic decisions. A convenience query cap must never redefine "every Shot." Change compares exact Shot-id sets: the frozen Baseline set against the genuinely new set. If either set is absent or incompatible, Comparability says why instead of estimating from counts.

57. **Provenance has two scopes.** Pixel, EXIF, Tone, Motion, bucket, and Change arithmetic are replayable from an exact Shot set and calculation version. Placement, framing, subject, and moment dimensions inherit model readings, so their Provenance includes every Analysis model and prompt version plus a per-Shot digest of the soft fields used. A changed digest forces re-baselining even when the prompt name stayed the same. This promises traceability rather than identical regeneration and supersedes decision 51 wherever it treats every Baseline figure as model-free.

58. **The Technique Map is evidence memory, not a curriculum.** Levels and prerequisites do not gate the map, the UI, or Scout selection. The map shows only what has been observed and what has recurred, with the supporting counts. Scout selects an Experiment Direction from the photographer's Tendency or an explicit request; if neither exists, silence is the honest result. No completion fraction, lock, unlock, level-up, or generic next step reaches the photographer.

59. **Generated references are outside the core loop.** Inspiration may be sourced when useful, but an issued Experiment does not automatically invoke Director or Veo. Director remains an optional legacy capability and must discard any generated blob if the Experiment closed while rendering. Experiment delivery, Criteria, Verdict, Change, and Journey never wait on or imply a generated clip.

60. **Longitudinal surfaces refresh with the event that changed them.** A live activity poll that sees new pipeline work reloads the Tendency Profile and Journey as well as Shots, Experiments, and Technique states. A correct Firestore record hidden behind stale client state is not a completed user-facing Journey Update.

61. **Scores are not part of the stored domain.** Overall and element scores are removed from Analysis, TechniqueState, migrations, API output, and client state. A lens may use an internal rubric to structure a reading, but that transient opinion cannot become a durable measurement or silently select a comparison.

62. **Vocabulary migrations include code seams, not only copy.** Experiment replaces Quest and challenge; Technique replaces skill everywhere except the legacy Firestore collection key `skills` and the migration-target class name `TechniqueState`; Shot replaces frame or photo when referring to the domain object. Findings, Experiments, Technique states, and blob helpers use their domain names so new code cannot accidentally revive the discarded concepts.

63. **A Companion interruption must show its warrant.** The Android pulse requires corroborated Evidence with at least two agreeing readers and confidence at or above the configured Companion threshold. The line includes the measured or corroborated fact that justified speaking. A Finding includes its `why`; unsupported technique labels remain silent.

64. **Experiment Record transitions are transactional.** Judge appends a Shot's Verdict at most once and changes `open` to `completed` in the same storage transaction. Skip and Expire may change only a record that is still open. Delivery and optional Director writes patch their own fields conditionally rather than rewriting a stale Experiment. Concurrent actors may race, but the winner cannot have its Verdict, status, or delivery state overwritten by the loser.

65. **Ask is a temporary Scene Probe, not another capture mode.** Only an explicit tap starts it. The client sends the current preview and active Experiment id to the existing preflight path; no Shot id is allocated, no blob is written, and no Analysis, Technique Evidence, Keeper state, or Journey input is created. The response is constrained to visible Criteria and one move. Missing Experiment, unreadable preview, unresolved Criteria, or weak support produces a refusal rather than generic photographic advice.

66. **Amber carries agency, not quality.** Across Android and web, ink is the surface, warm white is readable content, and amber marks only an offered or selected Experiment, a Companion suggestion, or the photographer's selected action. Amber never means that a Shot is good or that Change is improvement. A restrained red may mark a Finding that needs attention; generic green success is not part of the product language.

67. **A persisted Technique label cannot outrank its counts.** On every Technique-state read and write, the domain derives `unobserved`, `observed`, or `recurring` from attempts and corroborated sightings. Legacy `solid` or `rusty` rows with fewer than three corroborated sightings become `observed`; a migration may preserve Evidence, never preserve a contradictory grade. Journey and API surfaces therefore cannot call a Technique repeatable while showing zero corroboration.

68. **When the system retracts a claim, it writes the correction.** If a current evidence rule no longer supports a Technique named as recurring in the latest Journey Update, the next Journey recomputation writes a deterministic correction with the exact retracted Technique set. It does not rewrite the historical artifact, blame the photographer, or describe the correction as Change in their eye. The correction is code-authored, records no model provenance, and becomes the new latest Update.

69. **Explore asks a question and never grades the answer.** The current Explore implementation reused Reproduce mechanics: fixed Criteria, `criteria_met`, and a Shot-by-Shot path toward one accepted composition. Real-phone use showed the result clearly. The Experiment argued with the photographer instead of helping them explore. A corrected Explore offers two to four Variations, including a meaningful inversion where the Scene supports one. It records which explicit Shots tried which Variations, what Evidence appeared, and which became Keepers. It creates no Verdict and has no `met`, `not met`, `ready`, or `shoot again` state. The photographer may end it at any time. This supersedes decisions 6, 43, 54, 64, and 65 wherever they apply Reproduce completion rules to Explore.

70. **Experiment types own different evidence.** Reproduce alone declares checkable Criteria and asks Judge for a Verdict about deliberate repeatability. Compare preserves at least two Variations of one controlled decision and asks for an optional photographer preference; the model does not choose a winner. Explore records range and observed differences without a correct answer. Every Experiment may freeze a Baseline and later receive a Change when comparable evidence exists, but the absence of a Verdict is valid for Explore and Compare. The Experiment Record is type-specific rather than a Reproduce record with a different label.

71. **Open does not mean active, and an untagged Shot is free.** The one-open slot remains a planner invariant so Scout does not flood the photographer with offers. It does not claim the camera or subsequent archive. The camera starts in free mode. The photographer explicitly enters, pauses, resumes, or leaves an Experiment, and only an explicit `experiment_id` associates a Shot with it. Pausing clears camera participation without skipping the Experiment. Leaving records a neutral human decision, not failure. An untagged Shot still updates Analysis, Technique Map, Tendency Profile, and Journey, but Judge never treats capture time as submission. This supersedes decision 53 wherever `open` was interpreted as compulsory participation.

72. **Android and web are two clients of one Shoots identity.** Android signs in with the same verified Google identity as web and receives a revocable Shoots device session. The release build carries one stable service origin; no photographer enters a server address or transfers a pairing code. Android sends captured bytes directly to Shoots storage and publishes the same `media.new` event as any other source. Drive becomes optional import and export, not the camera's transport or the product's identity boundary. The code-pairing screen and Drive-mediated camera upload are transitional implementation only. This supersedes decision 1 and the pairing assumption in decision 35.

73. **Gemini Live is the summoned Scene Companion, not only a post-Shot review.** When the photographer summons it, Android streams microphone audio and low-rate Scene frames to the Shoots WebSocket relay. The relay opens Gemini Live server-side, provides current Intent, the optional Experiment, relevant photographic memory, and measured camera facts, then returns interruptible audio and transcripts. A guide tool receives cell refs and Android converts them to a human overlay. The model may ask, suggest, remember an explicit fact, or offer a Variation. It cannot capture a Shot. A direct Photographer statement may be remembered with transcript provenance, and the `remember` tool reports what it stored. A derived implication, inferred Intent, preference, or source role requires confirmation. The current post-session Listener merge lacks per-fact provenance and correction and remains migration work rather than target behaviour. Silence resumes when the session ends. A one-frame Scene Probe remains the no-audio and degraded-network fallback. This supersedes decisions 10, 17, 35, 47, and 65 wherever they restrict the Companion to a fixed reviewed Shot, a Criteria-only Ask, or unqualified Listener memory.

74. **The camera and the archive run on different clocks.** Foreground interaction cannot wait for the full Analyst panel. Android acknowledges Talk locally, prepares the Live transport without sending camera or microphone data before an explicit summon, and returns camera control after capture while upload and Analysis continue. Acceptance measures time to listening state, time to first Live audio, capture to ready camera, and capture to background pulse separately. On the real acceptance device, a ready Live Scene Session targets first audio at or below 1.5 seconds median and 3 seconds at p90 over at least 20 turns. Deep Analysis keeps the corroborating panel and publishes when complete; it never locks the viewfinder. The fast answer is a labelled Scene read, not a substitute for Evidence, Verdict, Change, or Journey.

75. **The personal friction is phone photography without a learning record.** The photographer uses the phone they own, selects a few Shots for Instagram, and cannot tell whether valued decisions are becoming deliberate or merely recurring by chance. Social engagement is not an artistic signal. Shoots uses the Camera archive, explicit Keepers, and Experiment participation; it never uses likes as Evidence of improvement.

76. **The system camera keeps the shutter.** The Android hackathon client is a Phone Source, not a CameraX replacement. A new approved Camera item is the event that starts the background workflow. Android uploads the original bytes and stable source reference, then WorkManager may continue after the UI closes. The product requests no camera or microphone permission for this path. This supersedes decisions 35, 47, 72, 73, and 74 wherever they make a custom viewfinder or Gemini Live part of P0.

77. **One unattended run has a terminal condition.** A run starts when an unseen Shot source reference arrives. It ends when every accepted Shot is durably accounted for as analysed, retrying, or terminally unreadable; Technique Map and Tendency Profile have been updated; Scout has either issued one supported Experiment or recorded why it stayed silent; and every attempted external write has a durable result. A later explicitly associated Shot starts another run that may add a type-specific Experiment result, Change, and Journey Update. The photographer supplies media and optional signals, not pipeline instructions.

78. **The web is the audit desk.** It shows current work, finished artifacts, abstentions, retries, and external writes. It does not require the photographer to press Analyse, update the Journey, find patterns, or choose the next Experiment. Android supplies phone Shots and import status; Drive is an optional import and reviewed-output adapter.

79. **Four-day scope favours a complete loop.** Automatic Phone Source ingress, idempotent direct storage, explicit Experiment association, one honest type-specific result path, Change, Journey, ActivityEvents, and a continuous Cloud proof are P0. Native Google sign-in, a custom camera, Gemini Live, weather, place facts, richer guides, and Compare are later. The existing pairing token may authenticate the demo Phone Source; it is not the release identity design.

80. **Run state, not event order, settles unattended work.** Every accepted Shot creates one Run before its first pipeline publish. Each stage writes its own outcome idempotently. The last required outcome closes the Run through one atomic mutation, so Scribe finishing before Cartographer cannot create a false terminal claim. ActivityEvents remain the explanation and live feed; clients read Run state for completion. A deterministic completion ActivityEvent may be replayed without creating a second audit fact.

81. **The hackathon Experiment is Reproduce or silence.** Scout issues Reproduce only when corroborated Evidence in a marked Keeper provides both the Technique and one exact reference Shot. It freezes that reference and Criteria before any result, and the Experiment Record accumulates only explicitly associated result Shot ids. An abstention still records the result Shot but creates no Verdict. Until Variations and photographer-owned Compare preferences exist, Scout does not issue Explore or Compare and never disguises Reproduce mechanics under either name.

82. **A Capture Session freezes participation before upload.** Android reserves one Capture Session for one open Reproduce before launching the system camera. On return it commits the exact ordered Camera source references selected by that explicit handoff. Each local import assignment keeps the Capture Session id durably before WorkManager uploads anything, and the server derives the Experiment id from the committed membership. An unrelated Camera item, a later preference toggle, or capture time alone cannot change that assignment. Only one nonterminal Capture Session may reserve an Experiment at once.

83. **A Reproduce batch settles as one batch.** Judge records every committed member, including abstentions and unsupported media, without letting the first result close the Experiment. Once every member has a Judge outcome or terminal media outcome, the batch completes Reproduce if any supported Verdict meets Criteria; otherwise the Experiment stays open for another explicit Capture Session. The representative result is the earliest Criteria-met member in committed order, or the latest judged member when none met. Every result remains in the Experiment Record. The Capture Session itself settles only after every member Run is terminal or complete.

84. **Android is the daily client; web remains the audit desk.** Android shows Now, the Shot archive, Keeper controls, the Reproduce Record, Technique Map, Tendency Profile, Change, and Journey from the same server truth as web. It may cache the last successful read for offline use, but local cache never becomes a second photographic record. The web keeps the deeper ActivityEvent and Run audit. Neither client owns separate Photographer state.

85. **Google identity and Drive authority are separate grants.** Android uses Credential Manager to prove the same Google `sub` used by web and receives a revocable device session. Drive remains an optional import and reviewed-output adapter. Android asks for `drive.file` only when the photographer chooses Connect Drive, sends the offline authorization code to the server, and stores no Google refresh token on the device. Revoking a device does not delete the Photographer record; deleting the account revokes devices and service access while leaving user-owned Drive files in place.

86. **Android navigation follows the photographer's decisions, not the pipeline.** `Now` answers only what is useful now: open the normal camera, recover an active Capture Session, or open the newest Shot result. `Shots` is the archive. `Experiments` owns the offered Reproduce, its exact Keeper reference, Capture Session action, and Experiment history. `Journey` owns longitudinal Change. Settings is a secondary destination, not a daily tab. Phone Source, Run, sync, permission, and Drive implementation state remain available behind progressive disclosure or the relevant Shot; they do not compete with the primary action on `Now`.

87. **Daily and on-demand Experiment requests share one honesty gate.** The daily tick may offer one supported Reproduce without being asked. The photographer may also ask Scout to check now or request a different supported direction. Neither path bypasses corroborated Keeper Evidence, the one-open Experiment invariant, constraints, recent-history filtering, or the exact frozen reference and Criteria. An unsupported request returns an evidenced silence; it never falls back to generic advice. Replacing an open Experiment is an explicit photographer action and records the earlier one as left.

88. **A Shot annotation points only where its Evidence reaches.** The default image layer is the first located measured Finding, otherwise the one supported Move or tested crop, otherwise the quiet human guide. A located Finding may mark its measured region, subject point, horizon, placement target, or pixel mask. A whole-frame Finding may mark the frame as a whole. A Finding such as shutter-based camera shake that has no local pixel region says so and invents no hotspot. Clean, Finding, action, and guide layers are selectable and only one instructional layer speaks at a time. Motion confirms layer changes, work transitions, and navigation; it does not decorate a static dashboard.

A later explicit Capture Session separately records that the Photographer entered the Experiment. This decision supersedes the automatic Experiment creation and Ask-first ordering in decisions 26, 95, and 104 while preserving their Evidence, one-open-Experiment, and no-inferred-Intent rules.

138. **A Deconstruction tells the selected Shot's visual story.** On explicit request, one bounded Scribe writer receives the chosen Shot and its stored Analysis Evidence. It writes a short opening caption and one to five distinct, supported story beats, each citing those exact Evidence ids. Page count follows the supported material, not a fixed chapter recipe. The writer explains visible relationships, light, colour, framing, and details; it does not narrate pipeline counts, invent the Photographer's Intent or a subject's feelings, award a grade, or infer an Experiment result. The image can disqualify a stored observation but is not permission to invent an uncited fact. Domain code validates references, length, and optional detail selections; this structural check does not prove semantic truth. The photographer reviews the model-written draft before sharing. Opening and story pages are 1080x1350 JPEGs. The last page is the same selected Shot at its original oriented dimensions and aspect ratio, without captions, branding, borders, overlays, or a forced crop; it is a clean JPEG export, not a camera RAW file. Detail crops use only stored cell references converted by grid math and are labelled as details; full-image pages preserve the framing. The writer cannot emit pixel coordinates or new visual geometry. Model and prompt provenance and the validated writing checkpoint are stored; a render retry reuses that writing, concurrent requests are leased, and failures remain visible without a hand-authored fallback masquerading as a model draft. Old drafts remain readable. Separate ordered image downloads on web and multi-image share/save on Android retain publication authority with the Photographer. No original, Analysis, Technique Map, or Journey is changed. This supersedes the fixed-length, template-caption export in decision 105, while retaining its source ownership and explicit cover selection.

139. **A Deconstruction connects its story to existing Visual Evidence Artifacts.** Scribe may select one stored Visual Evidence Artifact for a story beat that cites the same Technique Evidence. The writer sees the actual artifact preview, its legend, and its authority beside the clean Shot. Only a readable image belonging to that Shot and Photographer, with a matching source digest, current renderer version, rendered status, and measured or bounded verification is eligible. Unresolved, rejected, fallback, manual-fixture, stale, missing, or image-less artifacts are not offered. A subject contour also needs stored subject cells; its measured area may not exceed their context bounds. This rejects a broad background mask presented as a small subject, without claiming that a surviving contour is semantically proven. The artifact explains only its recorded measurement or located model read; it does not prove artistic quality, Intent, depth, or causation. The writer may reject a visually misleading artifact even after these checks. Code pairs the unchanged artifact with the full Shot and a short factual legend, without drawing new geometry, recolouring the artifact, or cropping away context. A beat selects either that artifact, an eligible detail crop, or the full Shot. No artifact is required when none helps. Opening and clean ending remain unmarked. Artifact byte digests join the writing checkpoint so changed or unavailable inputs cannot silently reuse a mismatched story. Web and Android export the same ordered JPEGs. This extends decision 138 without a new Analyst run or another agent.

140. **A Photographer may request a Deconstruction directly from a Shot.** The web Shot detail page can build, reopen, and download a visual story for that exact owned still Shot once its stored Analysis is usable. The Shot reading and measurements come first. A compact Visual story button below them is collapsed by default, including for saved drafts; opening it reveals small previews, optional caption text, and build or download actions. Expanding the controls never starts generation. This explicit selection supplies the opening Shot without requiring a Keeper mark, a settled Shoot, or an Experiment. Building a story never creates a Keeper or implies taste, Intent, or Experiment participation. The Shot-sourced draft is separate from Shoot- and Experiment-sourced drafts, which retain their existing cover rules and Journey entry. Reopening reads the saved draft without starting model work. Explicit requests reuse the same-input draft and writing checkpoint; changed Evidence is used only on an explicit rebuild. Missing originals, unavailable readings, video, Inspiration, and another Photographer's Shots are refused. Existing Evidence, visual artifact, lease, export, and review rules still apply. The original, Analysis, Technique Map, and Journey remain unchanged.

142. **A visual goal is not a universal camera setting.** Deep depth of field, shallow depth of field, and bokeh highlights describe visible relationships. A single aperture threshold cannot establish any of them across different lenses, sensor sizes, focus distances, and computational Camera modes. New Reproduce Criteria for these Techniques therefore declare the visible goal without an aperture requirement. Scout offers framing, distance, and focus actions instead of prescribing an f-number. The Judge uses the declared visual Evidence and abstains when that Evidence is insufficient. Other explicitly declared camera-setting checks remain hard checks. This supersedes copying the taxonomy's aperture heuristics into these three Techniques' Criteria, not the frozen contents of older Experiments.

    Camera Capabilities are a device-reported inventory of the apertures exposed for each Camera. One reported value means that Camera exposes no aperture choice; several values describe only that Camera, not a union of interchangeable lenses. An absent list remains unknown. Android may report this inventory without taking a Shot or changing Camera settings. It is equipment context, not Photographer Intent or proof of which Camera will be used next. It never substitutes for Shot EXIF and never constrains an unrelated imported Shot. Scout and Judge receive labelled equipment context, with unknown controls left unknown.

    An older Reproduce that used an aperture proxy for one of these visual goals receives a visible correction notice on Android and web. Its Criteria, submitted Shots, Verdicts, and exported files remain unchanged. It is not retried under silently revised rules. The Photographer can keep the record, leave it, and explicitly create a new Experiment with corrected Criteria. An already submitted, not-yet-judged member is accounted for with an abstention rather than another misleading Verdict. Scribe carries the same notice into any newly requested review or export; it does not silently rewrite existing Drive files or claim that an old result succeeded.

    The deployed single-focus client corrects a retired Experiment only on explicit request. A stable replacement id belongs to the old Experiment. A supported replacement and the old offer's transition to left commit together with the open focus. If the old offer is no longer the current open focus, correction refuses without changing it or another Experiment. An identical retry returns the same replacement, including after it closes. The old Criteria, Verdicts, result Shots and review bytes stay intact; no general multiple-Experiment creation is introduced.
